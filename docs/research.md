# 研究路径与结论

## 问题边界

实测设备提供 ADB 开关并显示变化的局域网端口，但缺少可操作的标准无线配对界面。初始连接进入 TLS 证书拒绝状态。电脑没有枚举到可用的电视 USB 调试设备，当时的线材和 USB 主从连接条件也不足以建立有线 ADB，因此后续研究聚焦局域网。

USB 未枚举无法单独证明厂家禁用了所有有线调试。端口会变化也无法证明它就是配对端口。研究分别验证传输、身份授权、系统组件权限和实际 shell，不从现象直接推断原因。

## 阶段与证据

| 阶段 | 方法 | 结果与后续决策 |
| --- | --- | --- |
| 系统设置探测 | 普通 APK 查询 Intent、导出 Activity、原生设置包 | 实测缺少可解析的标准开发者和无线调试入口，继续查厂商组件 |
| 本机 ADB 与转发 | 检测 ADB 协议 CNXN/AUTH/STLS、回环连接和桥接 | 改变连接位置没有解决证书身份问题，停止将桥接等同于授权 |
| 厂商诊断与工厂通道 | 普通 UID 探测 socket、服务状态、配对事务入口 | 可构造或发送请求不等于获得系统权限，未形成最终授权路径 |
| OTA 和固件分析 | 读取本机 OTA 识别信息，查找官方分发镜像，解包系统组件并检查调用链 | 取得同系列较早 V277 完整镜像用于分析；未取得当前 V487 完整镜像 |
| 当前固件核对 | 通过诊断 APK 查询当前设备 Provider、配置结构及相关服务行为 | 将旧镜像中的线索与当前 V487 实际配置交叉核对 |
| 配置回调实验 | 变更小范围配置后回读，保留原始字符串并恢复 | 确认存在系统服务消费配置的路径；测试外部文件失败的记录未作为成功证据 |
| ADB 公钥写入 | 临时添加 `ipelNode`，系统服务覆盖写入 `adb_keys`，恢复配置 | 原生连接返回 `device`、shell UID 2000；公钥匹配和配置恢复通过 |
| 电脑控制 | 原生 ADB、scrcpy、AppKit 控制台、配置导出 | 已验证画面、应用操作、截图、APK 安装及 70 组厂商配置导出 |
| 桌面输入修复 | 相同协议事件比较原版与补丁、检查 UI 树和按键释放 | TCL 点击与滚轮专用路径通过定向回归；最终主观滚动体验仍需反馈 |

## 授权机制

在同系列旧固件中分析到 `IpelService` 从 `IpelEngine` 的 `ipelNode` 读取路径和值，使用文件写入接口处理节点。当前固件的 Provider 允许普通诊断应用读取和更新该配置，系统服务随后以自身权限写入目标。

最终实验只增加 `/data/misc/adb/adb_keys` 节点，将电脑专用公钥加换行写入，再精确恢复原配置。实验结果包含独立 ADB 身份、`uid=2000(shell)`、SELinux Enforcing、断开重连、电脑 ADB server 重启后重连及配置比对。此后才进入应用安装和实时控制开发。

当前仓库公开自己编写的诊断代码、授权封装、scrcpy 补丁和脱敏验证摘要。厂商镜像和反编译代码没有再分发。复核其他固件时，需要自行从可信来源取得对应版本，验证镜像摘要、组件实现和权限，不能仅凭相同型号或配置名称推定可用。

## 未成立或未完成的推断

- 普通应用无法凭空授予自身 shell、系统签名或调试管理权限。
- 工厂服务的存在无法证明它已启动、对局域网开放或接受普通 UID 的命令。
- Provider 的 `updated=1` 不能证明文件已经写入，最终使用原生 ADB 回读验证。
- V277 用于寻找线索，实际授权发生在 V487；两者的服务实现和权限不能直接等同。
- 未执行电视降级、完整刷机、root、桌面替换，也未证明任意第三方 APK 均可安装。
- 配置存在统计、推荐和广告字段只能证明相应机制的配置面，无法单独证明发生了个人信息外传。

## 继续研究时的记录格式

每个新机型记录型号、完整固件、Android API、补丁日期、Provider 权限、原始配置摘要、临时变更、恢复回读、ADB 状态和 shell 身份。原始配置和密钥只在本地保留，公开报告只附脱敏字段。将“静态分析发现”“普通 UID 请求被接受”“系统产生效果”“最终功能验证”分开记录。
